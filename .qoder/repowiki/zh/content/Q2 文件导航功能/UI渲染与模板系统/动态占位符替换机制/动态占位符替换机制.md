## 占位符替换流程概述

`getWebviewContent()` 函数是 q2 模块中负责生成 Webview 内容的核心函数，其主要职责是通过读取 `q2.html` 模板文件，并将其中的动态占位符替换为实际值，最终返回完整的 HTML 内容。该流程始于函数接收当前路径参数 `currentPath`，随后调用 `getConfig()` 函数获取用户配置，包括侧边栏宽度、行间距、最近目录、回收站、固定状态和大小显示模式等。

在获取配置后，函数会验证路径的有效性，并通过 `getDrives()` 获取系统驱动器列表。接着，函数生成各类 HTML 片段，包括驱动器列表、回收站和最近目录。这些动态生成的 HTML 内容，连同从 `generateWebviewScript()` 函数获取的内联 JavaScript 脚本，将作为替换值注入到模板中。整个流程通过一系列 `String.prototype.replace()` 方法调用完成，确保最终返回的 HTML 内容包含了所有最新的动态数据。

## 正则表达式全局匹配机制

占位符的替换依赖于 JavaScript 的 `String.prototype.replace()` 方法和正则表达式。`getWebviewContent()` 函数使用全局匹配（`g` 标志）的正则表达式来确保模板中所有出现的特定占位符都被替换。例如，`/\{\{SIDEBAR_WIDTH\}\}/g` 这个正则表达式会匹配模板中所有 `{{SIDEBAR_WIDTH}}` 的实例。

正则表达式的构造遵循严格的模式：`\{\{` 匹配字面量的 `{{`，`SIDEBAR_WIDTH` 匹配占位符名称，`\}\}` 匹配字面量的 `}}`。这种精确的匹配确保了只有格式完全正确的占位符才会被替换，避免了对模板中其他内容的误操作。替换过程是顺序执行的，每个 `replace()` 调用都会返回一个新的字符串，该字符串作为下一个替换操作的输入，从而逐步构建出最终的 HTML 内容。

## 空格问题修复案例分析

`q2占位符空格问题修复.md` 文档详细记录了一个因占位符格式不一致导致的严重问题。问题的根源在于 `q2.html` 模板文件中的 `{{INLINE_SCRIPT}}` 占位符被错误地写成了 `{ { INLINE_SCRIPT } }`，即在花括号之间添加了空格。

由于 `getWebviewContent()` 函数中使用的正则表达式 `/\{\{INLINE_SCRIPT\}\}/g` 要求精确匹配 `{{INLINE_SCRIPT}}`，因此无法识别带有空格的 ` { { INLINE_SCRIPT } } `。这导致内联脚本未能被注入到最终的 HTML 中，使得 Webview 中的所有 JavaScript 函数（如 `updateResourceExplorer`, `hideAllContextMenus` 等）都未定义，从而造成文件列表无法显示、交互功能完全失效。

修复方案是将 `q2.html` 文件中的占位符修正为无空格的 `{{INLINE_SCRIPT}}`，使其与 `getWebviewContent()` 函数中的正则表达式完全匹配。修复后，脚本被成功注入，所有功能恢复正常。此案例凸显了在模板系统中保持占位符格式一致性的极端重要性。

## 替换顺序依赖关系

占位符的替换顺序并非随意，而是存在明确的依赖关系。`getWebviewContent()` 函数首先替换路径和尺寸相关的变量，如 `{{CURRENT_PATH}}`、`{{SIDEBAR_WIDTH}}` 和 `{{LINE_SPACING}}`。这些变量的值直接来源于 `getConfig()` 函数的输出，是后续处理的基础。

在路径和尺寸变量替换完成后，函数才处理脚本注入，即替换 `{{INLINE_SCRIPT}}` 占位符。这种顺序至关重要，因为 `generateWebviewScript()` 函数本身需要 `currentPath` 和 `currentSizeMode` 作为参数来生成脚本。如果脚本注入发生在路径变量替换之前，那么生成的脚本中将包含未替换的 `{{CURRENT_PATH_JS}}` 占位符，导致脚本逻辑错误。因此，必须先确保所有基础配置变量已正确替换，才能安全地注入依赖于这些变量的 JavaScript 代码。

## 占位符命名规范重构

项目经历了一次重要的占位符命名规范重构。最初，用于注入驱动器列表的占位符被简单地命名为 `{{DRIVES}}`。然而，随着功能的演进，为了更清晰地表明该占位符注入的是 HTML 片段而非纯文本，该占位符被统一重命名为 `{{DRIVES_HTML}}`。

这一重构过程不仅限于 `DRIVES`，还扩展到了其他类似的占位符，如 `{{RECENT_DIRS}}` 重命名为 `{{RECENT_DIRS_HTML}}`。这种命名约定极大地提升了代码的可读性和可维护性，使开发者能够一目了然地知道某个占位符预期注入的内容类型。更重要的是，它增强了系统的稳定性。统一的命名规范减少了因占位符名称不一致而导致的替换失败风险，确保了模板与替换逻辑之间的一致性，从而避免了类似空格问题的再次发生。
