## 配置类问题排查

### 命令未找到问题排查

当用户反馈“command 'qqq.q2' not found”时，应遵循以下排查链：

1. **检查 activationEvents 配置**
   - 确认 `package.json` 中 `activationEvents` 包含对应命令
   - 正确配置示例：`"onCommand:qqq.q2"`
   - 若使用 `"*"` 则为启动即激活，可能影响性能

2. **验证 main 入口配置**
   - 检查 `package.json` 的 `main` 字段是否指向正确的入口文件
   - 当前配置：`"main": "./src/qqq.js"`
   - 确认文件路径存在且可读

3. **检查扩展激活流程**
   - `qqq.js` 中的 `activate` 函数应正确导入并调用子模块
   - 子模块（如 `q1.js`、`q2.js`）必须导出 `activate(context)` 函数
   - 确保子模块的 `activate` 函数被正确调用

4. **验证命令注册**
   - 在子模块的 `activate` 函数中，使用 `context.subscriptions.push()` 注册命令
   - 确保命令名称与 `package.json` 中定义的一致

### vscode重复声明问题

#### 症状描述
扩展激活失败，控制台报错：
```
Activating extension 'undefined_publisher.qqq' failed:
Identifier 'vscode' has already been declared
```

#### 根本原因分析
`vscode` 模块在多个文件中被重复声明，导致变量冲突。具体冲突链如下：
- `src/qqq.js` 声明了 `const vscode = require("vscode")`
- `src/q1.js` 也声明了 `const vscode = require("vscode")`
- `src/q2.js` 同样声明了 `const vscode = require("vscode")`
- 当 `qqq.js` 通过 `require` 加载 `q1.js` 和 `q2.js` 时，触发重复声明错误

#### 解决步骤
1. **修改 `src/qqq.js`**
   - 删除 `const vscode = require("vscode")` 声明
   - 保留 `fs` 和 `path` 等 Node.js 原生模块
   - `qqq.js` 仅作为入口模块，不直接使用 VSCode API

2. **保持子模块独立**
   - `q1.js` 和 `q2.js` 保留各自的 `vscode` 声明
   - 子模块负责自身功能的实现和命令注册

3. **验证修复**
   - 重启扩展开发主机
   - 检查控制台输出是否显示“扩展激活中...”及“所有命令注册完成”
   - 测试 `Ctrl+V` 和 `F2` 命令是否正常响应

#### 预防措施
- 明确模块职责：入口模块不直接使用 `vscode` API
- 建立代码审查机制，禁止在工具模块中引入 `vscode`
- 使用静态分析工具检测重复声明

## 界面类问题排查

### q2界面加载失败

#### 常见原因
1. **占位符替换错误**
   - 模板文件 `q2.html` 中的占位符与替换逻辑不匹配
   - 如 `{{DRIVES}}` 与代码中期望的 `{{DRIVES_HTML}}` 不一致

2. **HTML格式异常**
   - 模板文件存在语法错误或未闭合标签
   - 特殊字符（如反斜杠）未正确转义

3. **CSS样式冲突**
   - 自定义样式覆盖了 VSCode Webview 的默认样式
   - z-index 层级冲突导致元素不可见

#### 解决步骤
1. **检查占位符一致性**
   - 确认 `q2.html` 中的占位符与 `q2.js` 的替换逻辑完全匹配
   - 重点检查：`{{DRIVES_HTML}}`、`{{RECYCLE_BIN_HTML}}`、`{{RECENT_DIRS_HTML}}`

2. **修复占位符空格问题**
   - 错误：`{ { INLINE_SCRIPT } }`（含空格）
   - 正确：`{{INLINE_SCRIPT}}`（无空格）
   - 使用正则表达式 `/\\{\\{INLINE_SCRIPT\\}\\}/g` 进行精确匹配替换

3. **验证Webview脚本注入**
   - 确保 `generateWebviewScript()` 生成的 JavaScript 被正确注入
   - 检查 `window.addEventListener('message')` 是否注册成功

4. **调试界面渲染**
   - 打开开发者工具（F1 → "Developer: Toggle Developer Tools"）
   - 检查控制台是否有 `ReferenceError` 或 `Uncaught` 错误
   - 验证 `fileList` 元素的 `innerHTML` 是否被正确设置

#### 预防措施
- 建立占位符命名规范，统一使用 `_HTML` 后缀
- 开发 `verify-placeholders.js` 脚本自动验证占位符匹配
- 在提交前进行界面功能测试

## 功能类问题排查

### Python脚本调用失败

#### 症状描述
执行粘贴操作时，Python 脚本 `kp.py` 未被调用或返回错误。

#### 根本原因分析
1. **脚本路径错误**
   - `runPythonScript()` 中的 `scriptPath` 计算错误
   - 脚本文件不存在或权限不足

2. **环境变量问题**
   - 未正确设置 `PYTHONIOENCODING=utf-8`
   - 缺少必要的 Python 包（如 `pywin32`、`PIL`）

3. **跨平台兼容性**
   - Windows 使用 `pywin32`，macOS/Linux 使用 `pyperclip`
   - 剪贴板访问权限未正确处理

#### 解决步骤
1. **验证脚本路径**
   - 确认 `kp.py` 位于 `src/` 目录下
   - 检查 `__dirname` 是否正确指向扩展根目录

2. **检查依赖安装**
   - Windows：`pip install pywin32`
   - macOS/Linux：`pip install pyperclip pillow`

3. **调试脚本执行**
   - 在 `runPythonScript()` 中添加日志输出
   - 捕获并记录 `stderr` 输出以定位错误

#### 预防措施
- 在 `package.json` 中声明 Python 依赖
- 提供依赖安装指南
- 实现优雅降级机制

### 剪贴板访问权限

#### 问题描述
在某些系统上无法读取剪贴板内容，导致粘贴功能失效。

#### 解决方案
- **Windows**: 使用 `pywin32` 库访问剪贴板
- **macOS**: 使用 `pbpaste` 命令行工具
- **Linux**: 使用 `xclip` 或 `xsel` 工具

#### 验证步骤
1. 手动测试命令行工具是否可用
2. 检查 Python 脚本是否有执行权限
3. 验证剪贴板数据格式是否正确

## 性能类问题排查

### 文件大小计算性能

#### 问题描述
递归计算大文件夹大小时导致界面卡顿。

#### 优化策略
1. **异步计算**
   - 使用 `Promise` 和 `setTimeout` 避免阻塞主线程
   - 实现 `calculateFolderSizeRecursive` 异步版本

2. **缓存机制**
   - 使用 `fileSizeCache` 缓存已计算的文件夹大小
   - 防止重复计算同一路径

3. **节流控制**
   - 对频繁触发的大小更新请求进行节流
   - 使用 `debounceRender` 防抖处理

#### 监控指标
- 单次计算耗时超过 500ms 触发警告
- 缓存命中率低于 70% 需优化

## 跨平台兼容性问题

### 回收站命令缺失

#### 问题描述
在 macOS 和 Linux 系统上，回收站相关命令不可用。

#### 解决方案
1. **Windows**
   - 使用 `wmic logicaldisk get caption` 获取驱动器列表
   - 使用 `explorer.exe /select,` 打开文件夹

2. **macOS**
   - 使用 `open -R` 在 Finder 中显示文件
   - 使用 `pbpaste` 读取剪贴板

3. **Linux**
   - 使用 `xdg-open` 打开文件夹
   - 使用 `xclip` 读取剪贴板

#### 验证步骤
1. 在目标平台测试驱动器列表获取
2. 验证文件打开和剪贴板功能
3. 检查错误日志中的平台相关异常
