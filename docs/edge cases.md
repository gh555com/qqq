












## 场景1：复制过程中关闭标签
根据代码分析，这两个场景的行为如下：

## 场景1：复制过程中关闭标签

**当前行为**：任务会**继续执行**，不会自动取消

流程：
1. `withProgress` 的后台任务**独立运行**，关闭标签不会触发 `token.onCancellationRequested`
2. 文件复制会**完成**
3. 当尝试 `replaceAnchorInDoc` 替换锚点时：
   - 如果文件**已保存**：`vscode.workspace.openTextDocument(uri)` 可以重新打开文档 → **替换成功**
   - 如果文件**未保存就关闭**：锚点丢失 → 返回 `false` → **触发回滚**

```
                   ┌──────────────────────┐
    关闭标签  ──→  │ 后台任务继续执行     │
                   └──────────────────────┘
                              ↓
                   ┌──────────────────────┐
                   │ 文件复制完成         │
                   └──────────────────────┘
                              ↓
              ┌───────────────┴───────────────┐
              ↓                               ↓
     文件已保存                        文件未保存
              ↓                               ↓
     替换锚点成功                      锚点丢失 → 回滚
```

## 场景2：VS Code 崩溃

**当前行为**：事务系统会**在下次启动时恢复**

流程：
1. **崩溃瞬间**：任务立即终止，文件可能已部分复制
2. **事务记录**：存储在 `globalState`（持久化），不会丢失
3. **下次启动时**：触发 `TransactionManager.recover()`

```javascript
// q1.js 第1537行 - 启动时触发恢复
if (!global.hasRecovered) {
    global.hasRecovered = true;
    TransactionManager.recover().catch(e => console.error(e));
}
```

`recover()` 会：
- 遍历所有未完成事务
- 执行 `rollback()` 删除已复制的文件
- 清理残留锚点

```
    VS Code 崩溃
         ↓
    任务立即终止（文件可能已部分复制）
    事务记录保留在 globalState
         ↓
    下次启动 VS Code
         ↓
    TransactionManager.recover()
         ↓
    回滚所有未完成事务
    （删除文件 + 清理锚点）
```

---

## 总结

| 场景 | 行为 | 文件状态 | 锚点状态 |
|------|------|----------|----------|
| 关闭标签（文件已保存）| 完成任务 | 保留 | 被替换为内容 |
| 关闭标签（文件未保存）| 回滚 | 删除 | 随文件丢失 |
| VS Code 崩溃 | 下次启动恢复 | 删除 | 下次启动清理 |

**设计优点**：崩溃恢复机制很健壮
